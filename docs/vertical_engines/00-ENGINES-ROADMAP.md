## 1. The thesis: NCE already *is* the spine the reference implementation hand-built

the reference implementation's "Enterprise Architecture" concept makes one architectural bet over and over: **"BOM is the backbone"** — quote, procurement, delivery, invoicing, asset register and service all reference the same BOM lines, and a separate "Cognitive Knowledge Engine" knowledge engine sits beside it. He had to build both the shared spine *and* the cognitive layer by hand in a Next.js/Prisma app.

**NCE already provides both, as core infrastructure:**

| the reference implementation hand-built | NCE primitive that replaces it |
|---|---|
| "BOM is the backbone" shared data model | `kg_nodes` / `kg_edges` cognitive graph (RLS per `namespace_id`) |
| "Cognitive Knowledge Engine" knowledge engine + Library UI | `memories` (embeddings + `content_fts`) + `v3_cognitive_ledger` |
| Hand-wired cross-module events | the graph + cron + RQ tasks + A2A bus |
| Per-feature Anthropic calls | NCE cognitive engine + MCP `TOOL_REGISTRY` |
| Module-by-module REST in Next API routes | dual-surface: MCP tool **and** admin REST route per capability |

**Consequence for us:** every vertical engine is *thin*. It does not own a data model — it **contributes typed nodes/edges to the one graph** and **registers tools**. The cross-engine intelligence the reference implementation's "Management / Executive" module (#19) wants — *"sales celebrates, operations cries"*, the cross-module risk radar — is not a separate feature we build; it **emerges for free** because every engine writes to the same cognitive graph. That is the entire reason to do this in NCE rather than as 14 Next.js modules.

This is also the **two-speed model in action** (see memory `project-nce-two-speed-dev-model`): the reference implementation's concept + the FE-dev's Portal sidecars are the *fast-track hacks*; this roadmap is the *clean-track* rebuild of each as a first-class, multi-tenant, maintainable NCE vertical that ships to every host through the pristine mirror.

## 2. Conventions every engine follows

Distilled from `VERTICAL_MODULE_PATTERN.md` and the netbox / dynamics365 reference verticals. These are non-negotiable so the 14 engines stay consistent and ride the mirror for free.

1. **Path** — `nce/vertical_modules/<name>/`, with `mcp_handlers.py` + a `TOOL_REGISTRY` entry as the only hard requirements. Add `client.py`/`auth.py`/`sync.py`/`ingestion.py`/`webhooks.py`/`<domain>.py` only as the domain needs them.
2. **Dual-surface** — implement each capability once as a pure-ish `do_<action>(engine, params) -> dict`, expose it twice: a thin MCP `handle_*` (for AI agents) **and** a thin admin REST `api_*` route (for the BFF/frontend/cron/scripts with **no model in the path**). Every read-only/deterministic capability gets a REST route.
3. **Graph contribution** — upsert `kg_nodes`/`kg_edges` with `ON CONFLICT DO UPDATE`, batch via `UNNEST`, entity_type prefix `<NAME>_<Entity>`. **⚠️ Ground-truth corrections (verified — `98-code-gap-audit.md`):** (a) `confidence` (0–1) is on **`kg_edges` only — NOT `kg_nodes`**; node confidence goes in `payload`/JSONB or a side table. (b) **No generic `source_id`** column exists — provenance is the generic **`origin_event_id` (UUID)** + a **per-vertical `<name>_source_id` (TEXT)** column added by migration where source-retirement is needed (D365 pattern, migration 024). *17 engines each adding a column doesn't scale → cross-cutting decision: one generic `source_system`+`source_id`, or accept per-vertical columns.* (c) **No central kg-upsert helper** (~6 inline copies; `dynamics365/sync.py:819-898` is the template) — write your own or build a shared one first.
4. **Semantic ingestion** — raw → MongoDB; indexed → `memories` (embedding + `content_fts`); cognitive metadata → `v3_cognitive_ledger`. Only verticals that hold unstructured text (agreements, support tickets, design notes) need this track.
5. **Multi-tenancy** — any own table gets `ENABLE` + `FORCE ROW LEVEL SECURITY` + `tenant_isolation_policy USING (namespace_id = get_nce_namespace())`, mirrored into `schema.sql` + a numbered migration. Namespaces opt into an engine via `metadata.<name>.enabled = true`.
6. **Config** — namespace every key `NCE_<NAME>_*` (enable flag, URL, token, tunables). Never put a host-specific key in `nce/config.py` (FE-5).
7. **Resilience** — `httpx.AsyncClient` (30s timeout) routed through `nce.http_resilience.request_with_retry()`; OAuth tokens Redis-cached in `auth.py`.
8. **Incremental + retention** — pull only changed data and **retain it inside NCE** (the D365 watermark/delta pattern, `f0b791a`/`16697d1`). This is what makes the `d365|both|nce` per-function source switch flip with **no data migration**.
9. **Config-as-IP** — the reference implementation's business logic lives in JSON weight/tolerance files, not code (`procurement-weights.json`, `procurement-tolerances.json`, `finago-chart-of-accounts.json`…). We lift the *engine* and keep the *weights* as namespace-scoped config so each tenant tunes its own.
10. **Build-vs-buy default — copy-and-improve, don't rent (user directive 2026-06-17).** Prefer **building native** over paying for an external SaaS we could own. Treat competitor/vendor research (Huma, Simployer, Jetbuilt, XTEN-AV, Icecat, …) as a **feature catalogue to replicate + improve**, *not* an integration shopping list. The default for any "integrate $VENDOR as the backend" is **flipped to "build it"** unless the vendor falls in a carve-out. **Carve-outs (the few externals we genuinely keep, and why):** legal **system-of-record** we can't lawfully replace (**Finago** GL); **national eID** we can't reproduce (**BankID** via a thin **Criipto/Signicat** broker — minimal, cheapest rail); **open-source we self-host** (no recurring spend — **NetBox**); **systems we're already migrating off** (**D365** → Sales/Support replace it); **third-party data feeds** we don't generate (**Nettailer/Netset** prices, **manufacturer telemetry/EOL** APIs); statutory **reporting endpoints** (**NAV**, PEPPOL). Everything else — HR (was Huma/Simployer), CLM authoring (was Oneflow's paid platform; build native, keep only the BankID rail), PIM, etc. — we **build and improve**. *(Open tension to resolve: Portal **ADR 0023** currently mirrors Oneflow; under this directive, prefer native CLM + the cheap BankID-direct rail over the paid Oneflow platform — flag for an explicit ADR-0023 revisit.)*
11. **Concurrency-correctness lives in the DB, not the app.** Races on shared mutable state must be made *impossible* at the database, never guarded by an app-level check that loses under concurrency: **stock decrements** use `UPDATE … SET qty = qty − n WHERE qty >= n` (row-lock; Inventory — prevents overselling); **schedule reservations** use a Postgres **`EXCLUDE USING gist`** exclusion constraint on a `tstzrange` per resource (Resources — prevents double-booking). Two planners / a planner + an auto-allocator / two concurrent picks of the last unit are real; the DB constraint is the only correct guard.
12. **Verified codebase ground-truth (the audit's binding facts — `98-code-gap-audit.md`).** Build against what the code *is*, not what the specs assumed: **(a) No migration version ledger** — `schema.sql` + every `migrations/*.sql` **re-execute on each boot** under an advisory lock; **all DDL must be idempotent** (`IF NOT EXISTS` / `DO $$`), there is no Alembic up/down, ordering is lexical, and core objects (RLS, `get_nce_namespace`, `v3_cognitive_ledger`) live in **migrations not `schema.sql`** (don't grep only `schema.sql`). **(b) `config.py` is a hand-rolled `_Config` class** (os.getenv helpers), **not** pydantic `BaseSettings` — add `NCE_<X>_*` as class attrs via `_int_env/_bool_env/_float_env/_secret`. **(c) No SQL `nce` schema** — `nce.embeddings`/`nce.http_resilience` are Python module paths; all tables are in `public`; the only SQL `nce.` is the GUC `nce.namespace_id`. **(d) The `settings` table is global (PK=`key`), not namespace-scoped** — per-namespace source-mode / config-as-IP needs a new RLS table.

### AI-role taxonomy (from the reference implementation's module map, adopted system-wide)

Every tool/feature is tagged with the autonomy level the engine is *allowed* to act at:

- **Watcher** — observes + alerts (no writes). e.g. EOL/SLA-breach/expiring-agreement detection.
- **Advisor** — analyzes + recommends, human decides. e.g. supplier ranking, PL suggestion, quote draft.
- **Actor** — executes *with confirmation*. e.g. generate PO, create project from signed quote.
- **Autonomous** — end-to-end, gated by value/risk thresholds. e.g. <50K project auto-tasking, recurring invoicing.

This maps directly onto the `TOOL_REGISTRY` flags: `mutation=False` ⇒ Watcher/Advisor; `mutation=True` + `admin_only` ⇒ Actor/Autonomous.

## 4. The shared cognitive graph (entity catalogue)

The point of NCE is that these are **one graph**, not 17 silos. Canonical node types (entity_type prefix per engine) and the cross-engine edges that make the graph intelligent:

**Core spine nodes** (written by multiple engines, the "BOM backbone" in graph form):
`CUSTOMER`, `SITE`/`ROOM` (= `FUNCTIONAL_LOCATION`), `QUOTE`, `BOM_LINE`, `PROJECT`, `PRODUCT`/`SKU`, `VENDOR`, `CONTRACTOR`, `PO`, `AGREEMENT`, `ASSET`, `EMPLOYEE`, `RESOURCE`, `ALLOCATION`, `WORK_ORDER`, `TICKET`, `INVOICE`.

**Key cross-engine edges** (where the emergent intelligence lives):
- `QUOTE -[contains]-> BOM_LINE -[references]-> PRODUCT` (Sales/System Design → Product)
- `BOM_LINE -[procured_via]-> PO -[from]-> VENDOR -[under]-> AGREEMENT` (Procurement → Vendors → Agreements)
- `PO -[posted_to]-> INVOICE -[recognized_in]-> PERIOD` (Procurement → Economy)
- `PROJECT -[freezes]-> SIGNED_BASELINE`; `PROJECT -[in_phase]-> GATE` (Sales → Project)
- `BOM_LINE -[installed_as]-> ASSET -[lives_in]-> ROOM -[covered_by]-> SLA` (Field Tech → Assets → Support)
- `ASSET -[monitored_by]-> TELEMETRY`; `TICKET -[about]-> ASSET` (Support ↔ Assets ↔ NetBox)
- `WORK_ORDER -[assigned_to]-> EMPLOYEE -[has]-> CERT/SKILL` (Field Tech → HR)
- `PROJECT/TICKET -[requires]-> RESOURCE_DEMAND`; `RESOURCE -[allocated_to]-> WORK_ORDER`; `EMPLOYEE|CONTRACTOR|VEHICLE|TOOL -[is_a]-> RESOURCE`; `ALLOCATION -[needs]-> TRAVEL_LEG/STAY` (Staff & Resources is the scheduling layer between Project/Support demand and Field Tech execution)
- `VEHICLE -[also_is]-> STOCK_LOCATION`; `INVENTORY_ITEM -[kitted_for]-> PROJECT -[staged_on]-> VEHICLE` (Resources ↔ Inventory material flow)
- `PROJECT -[generates]-> CASE_STUDY` (Project → Marketing)
- **Business Insights(16)** adds no operational edges — it **reads every engine via A2A** and writes only its own `BRIEFING`/`SCENARIO`/`KPI_SNAPSHOT` artifacts (the consumer the other specs' "feeds the #19 Morning-brief" lines point to).
- **Customer Portal(17)** projects `CUSTOMER -[sees]-> FUNCTIONAL_LOCATION` (rooms) with the `BOM_LINE.status`/`ASSET`-lifecycle Domino's tracker, and hands off `SERVICE_REQUEST -[becomes]-> TICKET` (Support) / `EXPANSION_INTEREST -[becomes]-> LEAD` (Sales) — never writing those nodes.
- **The "silence" the reference implementation flags:** `TICKET/ASSET -[failure_pattern]-> PRODUCT` — failure data must flow *back* to Product (better BOMs) and Sales (upsell). In NCE this is just an edge type; the cognitive engine surfaces it.

Every engine attaches `confidence` (0–1) to derived edges and `<name>_source_id` for retirement. This catalogue is the contract; per-engine specs refine their slice.

## 5. Deep-AI surface (what "deep AI interaction" means per engine)

NCE is a cognitive engine, so AI is not a bolt-on chat box — it is the way capabilities are exposed. Three layers:

1. **MCP tools** → every deterministic capability is callable by an agent (and by the BFF without a model). This is the A2A/agent substrate.
2. **Cognitive recall** → engines write to `memories`; the engine can answer *"why did this threshold change / what similar projects failed this way"* via embedding + ledger (the reference implementation's per-supplier learning, friction-cluster, AI-draft patterns generalized).
3. **A2A flows** → engines call *each other's* tools through the A2A server, so a single agent request fans across engines. Canonical A2A flows to design:
   - **Quote→Design→Procure**: Sales agent asks System Design for a BOM, which asks Product for missing specs, which asks Procurement for live TCO/availability.
   - **Receive→Match→Cascade**: Warehouse goods-receipt triggers Procurement 3-way match → Economy cascade.
   - **Install→Asset→Cover**: Field Tech work-order completion → Assets lifecycle enrich → Support SLA activation.
   - **Morning brief (the #19 Executive aggregate)**: one agent queries Economy + Project + Support + Sales tools and returns the cross-engine "1 risk + 1 opportunity" — pure A2A composition, no new engine.

The **on-demand AI rule** the user specified for Product (expand product info *only* when a product is added to a quote/design and info is missing — **never bulk-update all products**) is a system-wide discipline: AI enrichment is **event-triggered and scoped**, never a background sweep. Each engine declares its enrichment triggers explicitly.

**Tier 4 — Platform, growth & the consumer leaves**:
`HR(13)` (assignment infra for Field Tech/Project), `Marketing(14)` (pure consumer of Project data → outbound content), `Business Insights(16)`, `Customer Portal(17)`. The last two are **pure consumers/projections that build LAST** because they depend on every upstream engine producing structured data:
- **`Business Insights(16)` = the reference implementation's #19**, now a real engine: the cross-engine analytics/board layer the other specs all "feed." 5. **Deep-spec status** — ✅ **all 17 engines specced** (`01`–`17`). `15` (Staff & Resources) = scheduling layer; **`16` (Business Insights)** = the reference implementation's #19 promoted to a real engine (cross-engine analytics/board layer, pure A2A/MCP consumer); **`17` (Customer Portal)** = the room-centric external surface (replaces the poor existing portal), build = its security boundary. 16 & 17 added 2026-06-17.

## 9. Cross-engine contracts (binding)

After hardening-review of all four Tier-1 roots (Product, Procurement, System Design, Project), the conclusion is firm: **each per-engine spec is individually strong; the risk lives almost entirely in the *seams* between them**, and in two cases the specs directly contradicted each other (`SIGNED_BASELINE` frozen in both Sales and Project; the Nettailer feed ingested by both Product and Procurement). The same primitive — *candidate match → confidence → human-review merge → provenance* — recurs in Sales, System Design, Product and Procurement. So we spec the seams **once here, before any build batch**, as binding contracts. Three recurring failure modes: **(i) shared-node ownership/lifecycle races**, **(ii) multi-master writes / silent divergence**, **(iii) premature trust in AI or autonomous output.** Two named contracts (**A** ownership & lifecycle registry, **B** autonomy governance) plus one shared service (**entity-resolution**) cover them.

### 9.1 Contract A — Shared-node ownership & lifecycle registry
Every shared node type has **exactly one owning engine** (sole writer); all others **read or *propose*** (a proposal is a suggestion until the owner commits). Where a node has a **status state-machine**, there is **one writer-of-record per transition** (not one writer for the whole node). Ownership/authority hands off **only at explicit lifecycle transitions** — never ambiguous in between. The ingest of any **shared external feed** is owned by exactly one engine; others consume its projections, never re-ingest.

**Write-authority rule:** if an engine needs to change a node it doesn't own, it calls the owner's tool (A2A) or writes a *proposal* the owner reconciles — it never writes the node directly.

**`BOM_LINE` lifecycle state-machine (the 5-writer race, resolved).** `BOM_LINE` is touched by Sales, System Design, Procurement, Warehouse, Field Tech and Project — so ownership is **per field/transition**, with the *content* frozen at signature and only the *status* advancing afterward:
- **Content** (product, qty, price): **System Design** writes (design-intent) → **Sales** freezes at the signed baseline → **immutable** thereafter. A change after freeze is a **`CHANGE_ORDER`** (Project-owned), never an in-place edit.
- **`status`** advances on a single legal path with **one writer-of-record per transition**: `PLANNED` (Design/Sales) → `ORDERED` (**Procurement**) → `DELIVERED` (**Warehouse/Inventory**) → `INSTALLED`/`TESTED` (**Field Tech**). Only the named engine may write its transition; transitions are validated (no `DELIVERED` before `ORDERED`). A `CHANGE_ORDER` removing a line **locks the status field** against a concurrent `DELIVERED` write (the race the review flagged).
- **`actual_cost`** (distinct from the frozen quote price): **Economy's cascade is the ONLY writer** — its "the cascade is the only place BOM-line cost is updated" rule *is* this field's write-authority. This is the clean worked example: the "5-writer" `BOM_LINE` decomposes into **content** (Design→Sales-frozen), **status transitions** (Procurement/Warehouse/Field Tech, one each), and **actual_cost** (Economy cascade) — no field has two writers.
- **Hand-off to `ASSET` (the 6th toucher + the competing-state-machine resolution).** At install, **Field Tech writes the line's terminal status** (`INSTALLED`/`TESTED`) **and** creates the `ASSET` (`BOM_LINE -[installed_as]-> ASSET`). That is the single hand-off point: **`BOM_LINE.status` is truth for delivery progress *up to* install; the `ASSET` 14-state lifecycle takes over for operational life** (health/warranty/SLA). The asset lifecycle begins where the line's delivery progression ends — **no two competing "installed" truths.**
- **Project** edges `TASK`s onto the line and reads status; it never writes content, status, or cost.

**Shared-feed ingestion ownership (the Nettailer contradiction, resolved).** The ~295 MB Nettailer/Netset feed is **ingested ONCE**: **Product (2) owns the ingest and SKU identity** (catalog → `PRODUCT` nodes + `product_prices`). **Procurement (1) does NOT re-ingest** — it **consumes Product's projections** (supplier-price / BID / orderline views) over A2A/REST. One stream, one parse, one staleness clock. (Generalises: any feed feeding two engines is ingested by the identity-owner; the other consumes.)

### 9.2 Multi-master divergence & continuous reconciliation
Whenever NCE holds a copy of data another system also masters, the two **will** diverge. This is **not transitional** — it is the permanent, structural cost of mirroring, and it recurs in at least three places: **Sales** (`d365|both|nce` switch), **Economy** (NCE's computed/periodised internal books vs **Finago**'s legal GL), and any future mirrored source. Binding rules (a **shared `<engine>_divergence_log` + reconciliation discipline**, not a single reader function):
- **Truth-rule, declared per pairing:** name which side is authoritative for which purpose. D365/Sales: **NCE-primary** (D365 is compared, not trusted). Economy/Finago: **Finago is legal system-of-record; NCE is authoritative for operational decisions** (cascade, margin, dunning). The truth-rule is explicit, never implicit.
- **Continuous reconciliation, not a one-off:** every divergence → `<engine>_divergence_log` (entity, field, nce_value, ext_value, detected_at, **materiality**). Built in the engine's **first build phase**. Reconciling two financial/record systems is an ongoing discipline (a manual Finago journal NCE never saw; periodisation booked differently than predicted), not a `do_reconcile()` afterthought.
- **Materiality thresholds + drift alerts:** divergences above a configured materiality threshold raise an alert; small noise is logged but not paged. (Shared infra — see §9.6 standing tally.)
- **Flip gate (external-source mode):** a function flips `d365→nce` **only when its divergence log is clean over a defined window** ("prove parity" is meaningless without the log).
- **Write routing:** the resolver routes **writes**, not only reads — **write-through to the external system while a function is `d365`/`both`; native-only once flipped.**
- **Collision-proof identity:** source-prefixed IDs + a mapping table (extend `<name>_source_id`) the moment native edits are allowed, so a native record and an external record can never collide.

### 9.3 Premature-AI-trust discipline
AI **proposes; humans confirm** until calibration data proves precision. Vendor "X% automatic" figures (e.g. the reference implementation's "80% auto") are **not** launch defaults. Every AI-proposing engine ships **propose-only / human-confirms-100%**, records accept/override decisions to `v3_cognitive_ledger`, and **raises its auto-accept confidence threshold only from measured precision** — never from a marketing number. (Applies to System Design proposals, Product enrichment, Sales lead-scoring, Procurement ranking, etc.)

**Retrieval-grounded generation (the gate shapes generation, it doesn't post-hoc verify).** Any generative output that makes factual claims — Marketing case studies, Economy close-narratives, Project status reports, the Support troubleshooter, the Business-Insights board pack / "ask your business" — is **constructed from cited graph facts** (*pull fact → cite its node → template into prose*), **not freely generated then claim-checked.** Mechanically verifying that fluent LLM prose contains *only* graph-backed claims is itself a fallible AI task (you can't regex it), so "no hallucinated claims" is enforced by **how the draft is assembled**, not a downstream checker. Every claim carries its source-node link (auditable, retractable).

**Structural enforcement, never LLM-instruction (the general rule behind the above).** Any red line that an LLM could circumvent by phrasing must be enforced at the **data-access layer**, not by telling the model to behave. The sharpest case: the **HR no-ranking / EU-AI-Act red line** at Business Insights' **open NL surface** (`do_ask_business`) — *"average resolution time by technician"* / *"which team has most tickets"* are de-facto people-rankings. **The query path physically cannot return person-grain rows for comparison/ranking, regardless of phrasing** — aggregates by team/period/engine only. Telling the LLM to refuse is as weak as post-hoc claim-checking; the constraint lives in what the data layer will return.

**Money/legal-field hard rule (no auto-promote, regardless of confidence).** For any AI-extracted field that **drives money or a legal commitment** — Economy invoice amounts/PO-nr/accounts, Agreements terms (`kickbackTiers`/`frameDiscountPct`/`paymentTermsDays`/`volumeCommitment`), product cost — the confidence score sets **review *priority*, not sign-off**. Because Claude's confidence is **verbalized, not logprob-calibrated** (§Product A4), a self-reported "90" is not a basis to skip a human. These fields are **never auto-promoted to authoritative on self-reported confidence**, no matter how high; a human signs off before they post/rebate/rank. (The three OCR surfaces — Product specs, Economy invoices, Agreements legal terms — escalate in consequence in that order; Agreements is the sharpest.)

**AI-citable publishing is effectively irrevocable → a higher, durable consent bar.** Content published as **AI-citable** (Marketing's AEO/GEO JSON-LD + the MCP-queryable content channel) can be ingested by answer engines / LLM crawlers — `marketing_source_id` hard-retire un-publishes the **CMS copy, not** a model that already trained on it. So consent for *AI-citable* customer content is a **stricter, explicitly-durable** grant than consent for an ordinary (retractable) web page; right-to-retract covers the source artifact, never the downstream training copy. This is the consent-side counterpart to retrieval-grounded generation above (provenance makes a claim *auditable*; it does not make a *published* claim retractable from a third-party model).

### 9.4 Shared entity-resolution & node-ownership service (NCE core)
The same primitive recurs in ≥4 engines — Sales (deal identity across D365/native), System Design (functional-location intent vs as-built), **Product (golden-record dedup *and* BOM→SKU matching — two instances in one engine)**, Procurement (shared-feed identity). **Build it once in NCE core**, not per-engine fuzzy-match-and-merge; Product is its first and heaviest client. The contract:
- **`resolve(candidates, keys, normalizers) -> ranked matches + confidence`** — the single match primitive.
- **Merge-review queue** — proposed merges **below the auto-threshold are held for human confirm**. This is **distinct from enrichment-confidence review**: an identity false-merge is **silent and permanently poisons the graph** (everything hangs off node identity), so identity merges get their *own* measured, human-reviewable queue — *not* a key-tuple assumption. (The Product dedup key `(manufacturer, mfr_part_no)` both false-merges — `Cisco`/`Cisco Systems`/`CISCO`, dashed MPNs, regional variants — and false-splits at 552k scale; GTIN, the "universal key", is often absent on AV SKUs. This is more important than any AI feature.)
- **Normalization maps as config-as-IP** (e.g. manufacturer-name normalization) — per-tenant, not code.
- **Field-level provenance + survivorship** (source-trust > recency > confidence), auditable.
All writes go to `v3_cognitive_ledger`. Per-engine specs **reference** this service; they do not reinvent it.

### 9.5 Contract B — Shared autonomy governance (NCE core)
Every **Actor/Autonomous** tool that writes to the world (Procurement `submit_po` — *spends real money*; Sales signing; Product `enrich`; Project `sync_bom_tasks`/`advance_phase`; Resources `reserve`; Field Tech dispatch) goes through **one shared governance wrapper** — each engine must not reinvent its gate. Required for any self-triggering mutation:
- **Value + volume/rate ceiling** — promote Project's size-tier `automation-tiers.json` as the *value* axis, **plus** volume/rate caps (a value gate alone is insufficient).
- **Risk flags beyond value** — flagship customer, first-of-kind, regulated/public-sector → force human-confirm **regardless** of value band.
- **Idempotency** — *non-negotiable* for external writes (no double-order / double-sign / double-task on retry); idempotency key per action.
- **Counterparty allowlist** — auto-acts only to vetted suppliers/recipients.
- **Kill switch** — per-tool + global (ties into the existing `nce:tools:disabled` toggle).
- **Ledger audit** — every autonomous act → the audit ledger, re-derivable. *(Ground-truth: the autonomy ledger is **`event_log`**, not `v3_cognitive_ledger` — verified `98` §6. C2 today is **schema-only: migration 022 tables + a read-only API, ZERO enqueue/enforcement/decorator code** — a replayed mutating act is NOT a no-op yet; the wrapper is genuinely greenfield.)*
- **Default posture:** every world-writing tool ships **human-confirm-only**; autonomy is earned per-tool once idempotency + audit are proven. **`submit_po` is the sharpest blast radius in all 15 engines** (writes money to an external API) — human-confirm-first, multi-factor gate later, and since the Netset Order API is a stub anyway there is no reason to auto-submit at launch.
- **Customer-facing autonomy is the next-sharpest, and *anti-mission* if wrong.** Support's **auto-close** can silently suppress the exact dissatisfaction signal the engine exists to catch — a wrongly-closed ticket is a **silent churn driver** — so it stays human-confirmed **longest of any tool**. **Auto-dispatch** sends a real technician to a customer site (cost + customer-facing), and **automated churn-recovery outreach** is an autonomous customer-facing act bound by *"omsorg, ikke overvåking"* — all three carry the full Contract-B gate, and a churn/health score **never surfaces to the customer**.
- **Compounding autonomy across engine boundaries (chained gates → real spend).** A self-triggering act in one engine can fire a self-triggering act in another: **Inventory auto-restock (`do_create_restock_po` under `RESTOCK_CEILING`) → Procurement `submit_po` (its own gate) → real money out.** Two gates in series is fine, but Contract B must hold **across the boundary, not just per-tool**: a single **end-to-end idempotency key propagated along the chain** (an auto-restock retry must never create a duplicate PO request *or* a duplicate order) and **one audit trail spanning both decisions** ("Inventory decided to restock → Procurement decided to order"). Any chained-autonomy path declares its end-to-end key + spanning ledger entry.

### 9.6 Shared-core prerequisites & the infrastructure tally
The reviews surfaced two NCE-**core** building blocks the verticals *assume but don't provide* — they must be built (and hardened) in core **before** the verticals that depend on them, not as vertical features:

- **Partner-scope RLS primitive (security-critical).** Vendors'/Field-Tech's Partner Access Model Layer-1 needs row isolation *below* the namespace: a new session GUC `nce.partner_scope_id`, a `get_nce_partner_scope()` function, and contractor-session setup in `admin_app`/`a2a_server`. Today NCE only has `get_nce_namespace()`/`SET LOCAL nce.namespace_id`. Hard requirements: **defaults to DENY when unset** (never "see all in namespace"), and **ANDs with** the tenant policy. This is a **core RLS extension needing its own security-review pass** — a prerequisite for Vendors(4) restricted-access + Field Tech(12) partner access, not B3 vertical work. **Generalises to an external-PRINCIPAL scope — across THREE principal tiers of escalating threat:** **employee** (namespace) · **contractor** (partner-scope — known counterparty under contract) · **external customer** (Customer Portal(17) — **internet-facing and potentially adversarial**). Build it as `nce.external_scope_id` (principal-kind + scope-id), not contractor-only. **The customer tier RAISES the bar, it doesn't reuse the contractor case for free:** the security-review must explicitly cover the **adversarial-external threat model** (credential attacks, **IDOR via the scope GUC**, enumeration, session fixation, prompt-injection on any customer-facing assistant). Customer Portal is the **second engine making this primitive load-bearing (after Field Tech) and the more dangerous one.** Same egress rigor applies to **read-only MCP surfaces exposed to an external/3rd-party AI** (e.g. the board's own AI in Business Insights(16)): authenticated + rate-limited + fully who-asked-what audited + an explicit signed-off acceptance that data leaves NCE's control to that AI vendor. **Paired field-level half — the allow-list redaction pattern** (Vendors' `partner-redaction.json`): RLS scopes the *rows* a principal can see; the **explicit field allow-list** (never deny-list) scopes the *fields* — reused by **4 consumers**: Vendors partner-view, Sales public-quote, Customer Portal, and **Marketing drafts (redacted at draft-assembly time, not publish — margin/cost/internal never enter a draft)**. Build the allow-list redactor once.
- **Reactive graph-event / trigger mechanism.** "Engine B reacts to a node engine A wrote" is assumed across **≥6 specs** — Project ("BOM-line-status-change → auto-task"), Economy ("fires on invoice ingest"), Vendors ("subscribes to feed-produced upserts"), Assets (install → promote location, telemetry → proactive ticket), Support (asset-health drop → proactive ticket), and **Resources most acutely** (a **cert expiring in HR silently invalidates a future allocation** Resources already reserved — the expiring-cert Watcher must *react* to HR's change, not poll) — and **specified nowhere**. NCE's model is graph-writes + ledger, not pub/sub. Decide **once**: a graph-event/trigger bus, or a documented polling/watermark convention. **Codebase catch (verified — `98`): the real substrate already exists IN CORE — a transactional outbox** (`nce/outbox_relay.py` + `outbox_events` + DLQ + an unused `processed_outbox_events` dedup table + 2 live producers, cron-driven, post-commit). **So C4 is ~60% built, NOT "specified nowhere."** **Generalise from the outbox** (add a subscribe/publish interface + **emit on graph-write** — kg upserts emit nothing today — + wire the dedup table for idempotent at-least-once). The `netbox_nce` Django push plugin is the **WRONG target** (hardcoded namespace, `asyncio.run`-in-signal — the parallel bridge to avoid). Until the interface lands, every "subscribes/fires-on" is hand-waving.

**Standing tally — shared-core infrastructure the suite needs (build once, not per-engine):**
1. **Node-ownership + entity-resolution registry** (Contract A §9.1 + §9.4) — consumers: Sales, System Design, Product (×2), Procurement (feed identity), **Agreements (coverage matrix: GL supplier ↔ agreement `supplierId` ↔ canonical `VENDOR` must reconcile, or it emits false leakage/coverage)**.
2. **Autonomy governance** (Contract B §9.5).
3. **Divergence-audit + continuous reconciliation with materiality** (§9.2 — Sales both-mode, Economy↔Finago).
4. **Partner-scope RLS primitive** (§9.6 — security-reviewed core extension).
5. **Reactive graph-event / trigger mechanism** (§9.6 — **~60% built**: generalise the in-core **transactional outbox** `nce/outbox_relay.py`, add subscribe/publish + emit-on-graph-write + dedup; NOT the netbox_nce push).
6. **`d365|both|nce` source-mode resolver + retention** (§9.2 — **Sales + Support, and every future D365-sourced engine**) — the read/write dispatcher + incremental retention + the divergence audit (item 3) packaged as **one core service** both call, not re-implemented per engine. Subsumes theme D.

**Plus two consolidation services (thin shared services, build once, all callers use them — never re-implement):**
- **Shared pricing service** — DG-pricing `salgspris = kostpris/(1−DG%)` lives once; **Sales, Product, Procurement** call it (kills the inline `*0.7` and any second/third copy).
- **Shared signing service — one `SignTransport` interface, two implementations** (resolved via the Oneflow research + Portal **ADR 0023**, which already governs: *"mirror the Oneflow core 1:1, wrap differentiated value around it, never alter the core data model"*). **Sales** (quote/baseline) and **Agreements** (authored contracts) both depend on the *interface*, not the vendor — no more two webhook handlers / two credential sets / two SHA-256 fingerprint impls:
  1. **Oneflow** = the **CLM-backend + signing rail for contracts we author** (quotes-to-sign, SLAs we issue). It gives Norwegian **BankID (AdES)** + sealed verification PDF + audit trail + archive + two-layer lifecycle (`state` signing-phase vs `lifecycle_state` awaiting→active→ended) **for free**, and the Portal already has a read-only mirror (`steps_product/oneflow.py` → `portal_state.oneflow_contracts`, token-header auth, fire-and-pull webhooks).
  2. **Criipto/Signicat-direct** = the **pure BankID rail** for lightweight signing decoupled from a Oneflow document, to avoid Oneflow lock-in, or if any agreement ever needs **QES** (Oneflow tops out at AdES).
  **Boundary:** Oneflow is for contracts *we author*; it does **not** blind-extract arbitrary incoming third-party PDFs — that stays Agreements' native OCR pipeline. Keep the **graph, term-extraction, coverage matrix, and DealRoom pricing/margin native** (Oneflow knows only sale price).
  **One-vs-two-ceremony (resolved):** model a signed quote and a customer SLA as **two distinct contract objects** (separate `lifecycle_state` clocks — the quote freezes into `SIGNED_BASELINE`, the SLA runs awaiting→active→ended), but **default to a single BankID ceremony** (bundle into one Oneflow contract / one signing session) where commercially possible; force two ceremonies only when the SLA is genuinely independent. Per-deal flag, not a hardcoded rule. The **quote's** signature is the one that freezes `SIGNED_BASELINE`. (Vendor agreements are cleanly separate; only *customer* agreements overlap Sales.)

**Kickback-governance enforcement point.** The conflict-of-interest risk (Procurement step-5 rebate-steering; data originates in Vendors) is **enforced in Agreements**: its compliance audit (`do_run_compliance_audit` / AIContractGuard — discount-limit + restricted-clause checks) is the natural gate that answers *"is this rebate-chasing within the signed contract and within policy?"*. Procurement's `rebate_override` is checked against Agreements' terms + audit via A2A — so the suite's biggest ethics risk is **resolved by an engine that already holds the terms**, not left in Procurement's ranking.

## 10. Competitive positioning & the moat

Deep competitive analysis of the AV-platform incumbents lives in **`90-competitive-landscape-av-platforms.md`** (Jetbuilt · XTEN-AV · D-Tools). The finding that shapes the whole suite:
